# 第十章：自主实现、智能体生成代码与成熟算法库

## 1. 当前 core 是怎样来的

现在工作空间还包含独立的 `upstream/moveit2` 与 `upstream/ompl` 官方源码快照。
它们不是 `manipulation_core` 的自研代码，也没有替换当前运行的系统二进制包。
建议优先沿[成熟源码阅读路线](../guide/MoveIt源码阅读.md)理解实际工程，
再用本章与教学实现对照底层原理；目录归属见[架构分类](../guide/工作空间架构.md)。

`manipulation_core` 的算法体是本工程根据教材公式、经典论文与公开算法定义重新编写的，
没有从 OMPL、MoveIt、KDL 或 Pinocchio 复制实现。矩阵运算使用 Eigen，测试使用
GoogleTest，构建使用 ament/CMake。

这里要同时避免两个误解：

- 代码自主编写，不表示 RRT、DLS、DH 或 PID 是本工程发明的；算法知识来自成熟公开理论。
- 没有链接成熟规划库，不表示代码自动达到成熟库的可靠性、性能和适用范围。

你可以从 `package.xml` 和 CMake 看到本包不依赖 OMPL/MoveIt；实际 FR3 运行链则明确使用
MoveIt/OMPL。两条线的目的不同。

## 2. 同一个数学公式为何会有不同代码质量

以 RRT 的一句伪代码“找最近节点并向样本扩展”为例，真正实现要回答：

1. 状态是普通向量、角度环、SE(3)，还是带约束流形？
2. 距离怎样归一化，米和弧度如何比较？
3. 最近邻是 O(N) 扫描、KD-tree、GNAT 还是并行结构？
4. `steer` 是直线插值、微分约束积分，还是控制器 rollout？
5. 一条边怎样碰撞检查，能否越过薄障碍？
6. 终点是一个点、容差区域、多 IK 解集合，还是任务约束？
7. 超时后返回失败、近似解还是当前最优解？
8. 随机数、线程、缓存和 repeated solve 怎样管理？
9. 路径怎样 shortcut、平滑、时间参数化和再次验证？

两份代码都可能“符合 RRT 原理”，但上述决策不同，可靠性和效果会有数量级差距。

## 3. 教学实现与成熟库的具体差异

| 维度 | 本工程教学实现 | 成熟 OMPL/MoveIt 路径 |
|---|---|---|
| 目标 | 逐行理解、可手算、回归公式 | 广泛机器人问题和长期维护 |
| 状态空间 | 任意维向量和盒状限位 | SO(2)/SO(3)/SE(3)、复合/约束空间 |
| 最近邻 | 线性扫描 | 可替换高性能近邻结构 |
| 碰撞 | 用户回调+离散直线检查 | PlanningScene/FCL、自碰撞、环境、缓存 |
| 约束 | 起终点向量 | 位姿/路径/可见性/多目标约束采样 |
| 算法 | 四种核心教学 planner | 大量树、路网、最优与并行 planner |
| 终止 | 迭代数 | 时间、外部条件、近似解、持续求解 |
| 后处理 | 随机 shortcut、单段五次 | 路径简化、响应 adapter、时间参数化 |
| 性能 | 小问题清晰优先 | 数据结构、缓存、并行和多年优化 |
| 验证 | 单元不变量与小障碍 | 大规模测试、benchmark、用户反馈 |
| 兼容性 | 当前编译器/工程 | 稳定 API、插件、版本与发行维护 |
| 安全 | 明确不可直接上真机 | 仍需厂家控制、安全层和系统验收 |

成熟开源库也不是“数学上永远正确”。版本、参数、碰撞分辨率、模型质量和使用方式都可能
导致失败；它的优势是边界处理、测试和维护证据更充分，而不是免于验证。

## 4. 为什么工程通常使用成熟开源库

### 4.1 总工作量不在核心十几行伪代码

基础 RRT 的主循环很短，但状态空间、约束、碰撞、数据结构、停止语义、路径处理、日志、
线程安全和集成占据更多工程量。成熟库把这些可复用工作集中维护。

### 4.2 正确性来自持续证据

机器人规划的危险错误往往不是立即崩溃，而是漏碰撞、角度环绕错误、奇异数值、错误近似解
或极端场景超时。长期测试、论文对照、benchmark 和不同用户场景能提供单次生成代码没有的
证据。

### 4.3 性能依赖数据结构和系统集成

机械臂规划常把大部分时间花在碰撞检测和最近邻搜索，而不是算法名字对应的主循环。成熟
实现会提供缓存、专用近邻结构、状态采样器、投影和并行工具。

### 4.4 可维护性和互操作性

MoveIt 的 planner plugin、PlanningScene、RobotTrajectory 和 controller 接口，让模型、
规划器和执行层可以分别替换。自行实现若没有相同合同，很快会变成无法测试的专用脚本。

## 5. 智能体直接写算法代码会发生什么

智能体很适合：

- 把公式变成最小可读实现；
- 生成手算例、有限差分与性质测试；
- 建立统一接口和文档；
- 为研究想法快速制作原型；
- 阅读成熟库后帮助解释数据流。

它不能自动提供：

- 未被测试覆盖的边界正确性；
- 渐近完备/最优证明与实现假设完全一致的保证；
- 在真实模型、狭窄通道和长时间运行中的统计证据；
- 硬实时、功能安全或厂家认证；
- 对未来依赖版本变化的自动维护承诺。

常见风险包括把论文伪代码漏掉一个条件、误用坐标系、用离散检查穿过薄障碍、只测试成功
案例、以固定随机种子的偶然结果当性能结论，以及在数值奇异处产生表面合理的输出。

## 6. 正确的组合方式

推荐“双轨制”：

```text
教学/研究轨：公式 -> 最小实现 -> 不变量测试 -> 与成熟库差分对照
生产运行轨：MoveIt -> PlanningScene -> OMPL/其他pipeline -> controller -> 仿真/实机
```

只有当自研算法在基准集上展现明确收益，才把它封装为 planner plugin 或 adapter。接入前的
最低检查包括：

1. 单元性质：限位、端点、路径连续、全部边有效、失败不返回伪解；
2. 差分验证：同一小问题和 OMPL/解析结果交叉检查；
3. 随机统计：大量 seed、成功率、P50/P95 时间、路径质量；
4. 消融实验：分辨率、步长、goal bias、样本数分别变化；
5. 故障注入：空空间、完全阻塞、薄障碍、窄通道、起点碰撞；
6. 性能剖析：碰撞检查次数、最近邻时间、内存；
7. 系统验证：规划结果重新由 PlanningScene 验证并完成时间参数化；
8. 仿真长期运行；真机则另加实时、安全、限幅、急停和厂家合同验收。

## 7. 什么时候应该自己写，什么时候不应该

适合自主实现：学习、验证推导、建立极简基线、研究新 cost/sampler/constraint、为成熟库写
回归测试、处理确实没有现成实现的新问题。

应优先使用成熟库：通用机械臂避障、要可靠交付、需要复杂碰撞/约束、要兼容多机器人、
现场维护成本高或涉及真实硬件风险。

最专业的做法通常不是二选一：自己写到足以理解和验证，再让成熟库承担生产运行；研究创新
只替换有明确假设和验收指标的那一层。

## 8. 对本工程的最终判定

- `manipulation_core`：项目自主教学实现，适合学习、测试和算法原型；
- `robot_franka_moveit_config/config/ompl_planning.yaml`：成熟 OMPL planner 的运行配置；
- `manipulation_moveit_adapter`：把参数化目标转为 MoveIt 请求；
- FR3/FR3 Duo 实际规划：仍由 MoveIt + OMPL 完成；
- 自研 planner 当前没有接真实执行链，这是刻意的安全边界，不是遗漏。
