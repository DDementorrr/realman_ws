# 第七章：MoveIt、ros2_control、Gazebo 的接口与数据流

## 1. 每个模块负责什么

| 模块 | 输入 | 输出 | 不负责 |
|---|---|---|---|
| RViz MotionPlanning | 交互 marker/按钮 | MoveGroup 请求、路径显示 | 物理执行事实 |
| 自定义 target adapter | PoseStamped/服务 | MoveGroup 请求 | 碰撞算法本体 |
| MoveIt move_group | 模型、场景、目标、当前状态 | RobotTrajectory | 电机闭环 |
| IK plugin | 位姿、seed、限位 | 候选 q | 全路径规划 |
| OMPL | start/goal/有效性 | 几何路径 | 物理动力学 |
| trajectory processing | 路径、限制 | 定时轨迹 | 控制硬件 |
| MoveIt controller manager | 轨迹与关节集合 | action goal | 控制周期 |
| ros2_control controller | 定时关节目标、反馈 | 硬件命令与 action result | 全局规划 |
| gz_ros2_control hardware | 模拟 joint state/command | Gazebo 关节作用 | MoveIt 语义 |
| Gazebo | 模型、力、约束、时间 | 物理状态 | 任务规划 |

## 2. 从拖动目标到机械臂运动

```text
RViz interactive marker / PoseStamped
  -> MoveGroup goal constraint
  -> IK sampling + PlanningScene collision checks
  -> OMPL path
  -> time parameterization
  -> controller selection by joint names
  -> FollowJointTrajectory action
  -> ros2_control position controller
  -> gz_ros2_control command interface
  -> Gazebo physics changes joints
  -> joint_state_broadcaster publishes /joint_states
  -> robot_state_publisher publishes TF
  -> RViz displays the same feedback state
```

因此 RViz 与 Gazebo 同步的正确办法不是两边各自动画一次，而是两者读取同一
`/joint_states`。执行成功必须来自控制器 action result。

## 3. 为什么有两份 robot_description

本工程严格分离：

- `/robot_description`：官方纯模型，给 MoveIt/RViz/正常 robot_state_publisher；
- `/robot_description_gazebo`：注入 `gz_ros2_control` plugin 和 command/state interface，
  只服务 Gazebo 后端。

如果把 FakeSystem URDF 发布给 Gazebo controller manager，关节可能在 RViz 中看似运动，
Gazebo 却不动；反向把仿真插件模型当规划模型，会把后端细节泄漏到 core。运行验证脚本会
检查两份描述没有串线。

## 4. 启动门控为什么重要

正确次序：

```text
Gazebo paused
 -> spawn robot
 -> load controllers inactive
 -> unpause physics
 -> activate controllers
 -> start MoveIt/RViz/adapters
```

FR3 ready 位姿在 Gazebo hardware 初始化时设置；控制器激活前暂停可避免重力作用下腕部
自由坠落。如果 spawn/configure/activate 任何一步返回非零，launch 立即关闭，而不是让
MoveIt 在一个半初始化系统上发送轨迹。

实现见 `manipulation_bringup/launch/franka_moveit_gz.launch.py` 的 OnProcessExit gates。

## 5. 配置文件如何配对

必须让这些字符串完全一致：

```text
URDF joint name
 = SRDF planning group joint
 = kinematics group member
 = ros2_control controller joint
 = MoveIt controller joint
 = trajectory goal joint name
```

tip link、base frame 和 controller action namespace 也必须一致。之前 Panda hand 的失败就是
MoveIt 找到了 hand controller 配置，却没有对应 action server，导致第二段轨迹发送失败并
取消已发送的 arm 轨迹。

## 6. 当前接口

单 FR3：

```text
topic /manipulation/fr3/target_pose  geometry_msgs/PoseStamped
group fr3_arm
controller /fr3_arm_controller/follow_joint_trajectory
```

固定 FR3 Duo：

```text
/manipulation/left/target_pose   -> left_arm independently
/manipulation/right/target_pose  -> right_arm independently
/manipulation/dual/left_target_pose  --+
/manipulation/dual/right_target_pose --+-> call /manipulation/dual/plan_execute
group both_arms -> left + right controllers
```

## 7. 诊断顺序

规划失败：查 TF/模型、start collision、IK、目标约束、planning scene、规划时间。

规划成功但执行失败：查 active controller、action 名称、joint 集合、起点容差和 action result；
不要先改 IK。

Gazebo 与 RViz 不一致：查 joint state 唯一来源、use_sim_time、描述是否串线和 controller
interface 是否 claimed。
