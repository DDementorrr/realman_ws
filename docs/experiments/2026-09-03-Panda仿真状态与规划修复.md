# Panda Gazebo 初始状态与规划失败实验报告

## 实验目标

定位并修复以下关联现象：

1. Gazebo/RViz 初始姿态偏离 MoveIt 官方 demo，腕部在启动阶段自由摆动。
2. RViz 末端交互目标不能完成规划。

## 根因与证据

MoveIt/RViz 与 Gazebo 需要相同的运动学模型，但需要不同的 ros2_control hardware backend。原 launch 同时把 GazeboSystem URDF 作为生成实体的字符串传入 Gazebo，又由主 `robot_state_publisher` 在公共 `/robot_description` 发布 MoveIt FakeSystem URDF。

`gz_ros2_control` 默认订阅公共话题，运行日志明确显示：

```text
controller_manager: Received robot description from topic
class mock_components/GenericSystem ... does not exist
Declared types are gz_ros2_control/GazeboSimSystem
```

进一步检查显示三个 controller 均为 `inactive`，hardware interface 列表为空，`/joint_states` 没有有效输出。因此：

- Gazebo 未获得位置保持/轨迹控制，重力导致腕部自由运动和初始姿态漂移。
- MoveIt 没有完整实时关节状态，规划场景的 current state 不完整，RViz 交互规划会失败。

用户给出的 Gazebo `exit code -2` 与 move_group `exit code -15` 出现在 Ctrl-C 后，分别对应 SIGINT 和 launch 超时后升级 SIGTERM，是关闭阶段现象，不是规划失败原因。

## 修复

- `/robot_description`：仅供 MoveIt、RViz 和主 `robot_state_publisher` 使用。
- `/robot_description_gazebo`：仅发布含 `gz_ros2_control/GazeboSimSystem` 的 URDF。
- 在 Gazebo 插件内加入 `/robot_description` 到专用话题的 remap。
- 显式配置 `hold_joints=true`，在 controller 接管前保持未认领关节。
- 将启动门控改为“暂停生成实体 → hardware 初始化 → controller 配置为 inactive → 解除暂停 → controller group 原子激活 → MoveIt/RViz 启动”，彻底去除受重力影响的启动窗口。
- 所有门控步骤仅在前一步退出码为 0 时继续；失败时直接关闭 launch，防止以半初始化状态进入 MoveIt。

## 回归结果

### 控制与状态

- `PandaGazeboSystem`：`active`。
- `joint_state_broadcaster`、`panda_arm_controller`、`panda_hand_controller`：全部 `active`。
- 7 个臂位置命令接口和 `panda_finger_joint1`：全部 `available` 且 `claimed`。
- `/joint_states`：约 200 Hz。
- 初始臂关节：约 `[0, -0.785, 0, -2.356, 0, 1.571, 0.785]`，与上游 `initial_positions.yaml` 一致；观测速度接近零。
- 启动阶段：模型在 controller 接管前保持暂停，不再出现腕部自由摆动。

### 规划与执行

向 `/manipulation/target_pose` 发布目标：

```text
frame=panda_link0
position=(0.35, 0.0, 0.59)
orientation=(1.0, 0.0, 0.0, 0.0)
```

结果：OMPL/RRTConnect 规划成功，`panda_arm_controller` 接受轨迹并报告 `Goal reached, success!`，MoveIt execution 和目标 adapter 均返回 `SUCCEEDED`。这条路径与 RViz MotionPlanning 面板使用相同的 move_group、current state 和 controller 执行链。

夹爪 action `/panda_hand_controller/gripper_cmd` 的类型为 `control_msgs/action/ParallelGripperCommand`；发送 `panda_finger_joint1=0.02` 后 action 返回 `SUCCEEDED`。

静态测试结果：相关 4 个包构建成功，`manipulation_demo` 的 2 个测试全部通过；环境验证脚本全部通过。

## 结论与建议

本次两个现象来自同一描述话题污染问题，现已修复。若 RViz 偶发对某个拖动目标显示规划失败，应先缩小位姿变化并确认交互标记颜色；单个目标无 IK 解、超出工作空间或处于自碰撞仍属于正常的目标不可达，而不是控制器故障。运行期可执行：

```bash
/home/ww/scripts/verify_panda_gz_runtime.sh
```

只有该脚本通过且 MoveIt 返回规划结果后，才应继续分析具体目标的 IK、碰撞或规划器参数。
