# Panda arm+hand 执行故障实验报告

## 结论

故障不在 IK、规划算法或 RViz，也不是“手爪 controller 没有被加载”。直接原因是 MoveIt 与 `parallel_gripper_action_controller` 对同一 action 名称声明了不同的 action 类型：

```text
MoveIt client: control_msgs/action/GripperCommand
controller server: control_msgs/action/ParallelGripperCommand
name: /panda_hand_controller/gripper_cmd
```

ROS 2 action 发现同时要求名称和类型匹配，所以 server 名称可见不代表 MoveIt 的强类型客户端已连接。

## 证据链

1. `panda_hand_controller` 状态为 `active`，排除 controller 未加载。
2. 串行启动 `joint_state_broadcaster -> arm -> hand -> move_group/RViz` 后仍可复现原错误，说明启动竞态不是充分解释。
3. Jazzy 上 `parallel_gripper_action_controller/GripperActionController` 实际导出 `ParallelGripperCommand` server，而 MoveIt Simple Controller Manager 同时提供 `ParallelGripperCommand` handle。
4. 修改后 MoveIt 日志显示 `Added ParallelGripperCommand controller for panda_hand_controller`。

## 修复

文件：`manipulation_ws/src/moveit_resources/panda_moveit_config/config/gripper_moveit_controllers.yaml`

```yaml
panda_hand_controller:
  action_ns: gripper_cmd
  type: ParallelGripperCommand
  default: true
  joints:
    - panda_finger_joint1
```

保留了启动就绪顺序，因为它可以避免 controller 尚未 active 时就进入执行；但 action 类型修复才是本次故障的根因修复。

Gazebo 主启动不长期依赖这个上游文件；相同契约已放入项目自有的 `manipulation_bringup/config/panda_moveit_controllers.yaml`。

## 回归结果

在 `mock_components` 后端中发送一条同时包含 7 个 arm joint 和 `panda_finger_joint1` 的 `moveit_msgs/action/ExecuteTrajectory` 轨迹：

- `panda_arm_controller`: goal accepted，`Goal reached, success!`
- `panda_hand_controller`: `Received & accepted new action goal`
- MoveIt TrajectoryExecutionManager: `Completed trajectory execution with status SUCCEEDED`
- `/execute_trajectory`: MoveIt error code `val: 1`，action 状态 `SUCCEEDED`

该结果验证 MoveIt—ros2_control—FakeSystem 的 arm+hand 执行契约，不等价于 Gazebo 物理或真机验收。

## 其他日志的性质

- controller manager 偶发 100 Hz overrun：WSL2 调度抖动，本次不导致执行失败。
- Octomap 无 3D sensor plugin：当前未配置环境感知，不阻塞无障碍 A→B。
- `/recognize_objects` 不存在和 RViz Visual Tools panel 缺失：可选 UI/感知功能，与 controller action 无关。
