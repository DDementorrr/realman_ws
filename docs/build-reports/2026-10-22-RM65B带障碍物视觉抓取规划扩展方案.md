## 1. 报告目的与结论

本文规划在现有 RM65B + CTM2F110 + 腕部 RGB-D 相机 Pick & Place 仿真基础上，增量增加以下能力：

- 可配置的半环形或环形扩展工作台；
- 薄墙、方块和长方体等障碍物；
- 固定种子、可重复的随机障碍物场景；
- 由 RGB-D 深度数据估计障碍物位置和包围盒；
- 将感知障碍物同步到 MoveIt PlanningScene；
- 在同一任务中保留多组抓取和运输候选轨迹，并按安全性和代价选择；
- 保持现有 `/object_pose`、`/place_pose` 和 MTC Pick & Place 接口不变。

阶段 0 已按修订范围验收；阶段 1—3 已完成静态工作台、固定/随机障碍物和静态真值更新；阶段 4 已完成静态 RGB-D 几何与独立回放；阶段 5 已完成单薄墙、RGB-D 障碍和独立已知目标的固定附着仿真闭环及失效回归；阶段 6 已完成同一 RGB-D 范围的多候选、硬约束评分、归档绑定及完整执行验收。阶段 0—6 各自有界出口已完成，不能将其合并外推为纯图像目标定位、任意障碍布局、真实接触或实机验收。阶段 0 原范围依据仍为 2026-10-24 审查报告；Gazebo、MoveIt、MTC、腕部相机和视觉定位兼容入口保留。

**工作台扩展前必须通过下文修订后的 S0-A—S0-D：公共包可独立构建、入口可独立启动、标准消息/配置可替换、原固定附着仿真可用。** 阶段 0 不承担通用执行平台、真实数据采集或实机迁移认证；后续功能继续遵守公共包不反向依赖仿真包的边界。

迁移目标是“共用感知、场景管理、MTC 和候选评估代码，通过独立配置及适配器切换数据与执行来源”。代码可复用不等于参数、规划轨迹或实机效果可直接复用；实机标定、控制后端和运行验收另行进行。

## 2. 当前基线与约束

当前已存在的上层接口如下：

| 接口 | 类型 | 用途 |
|---|---|---|
| `/object_pose` | `geometry_msgs/msg/PoseStamped` | 目标物体位姿，通常转换到 `base_link` |
| `/place_pose` | `geometry_msgs/msg/PoseStamped` | 放置目标位姿 |
| `/pick_place/solution` | MTC 解消息 | 规划结果观察和记录 |
| `/pick_place/plan_ready` | `std_msgs/msg/Bool` | 完整 MTC 任务是否规划完成 |
| `/camera/camera/color/image_raw` | `sensor_msgs/msg/Image` | RGB 图像 |
| `/camera/camera/depth/image_rect_raw` | `sensor_msgs/msg/Image` | 深度图像 |
| `/camera/camera/color/camera_info` | `sensor_msgs/msg/CameraInfo` | 彩色相机内参 |
| `/camera/camera/depth/color/points` | `sensor_msgs/msg/PointCloud2` | 深度点云 |

必须继续遵守以下边界：

1. 视觉层不直接调用 MTC、控制器或 `ApplyPlanningScene`，只发布目标、障碍物及质量信息；现有视觉节点的场景写入职责必须在阶段 0 拆出。
2. MTC 不依赖 ArUco 的具体实现，只消费统一位姿和 PlanningScene。
3. 已知几何验证模式下，Gazebo 和 MoveIt 使用同一份通用场景几何，经各自适配器转换；视觉验证模式下，规划障碍物来自真实图像/点云处理，Gazebo 真值仅用于评估，不能暗中补入感知结果。
4. 与规划相关的场景几何、目标或模型配置变化后，旧候选失效，PlanningScene 更新后重新规划；不删除仍然有效的整个场景，也不因原始点云每帧噪声无条件使全部候选失效。
5. 当前仓库只验证 Ubuntu 22.04、ROS 2 Humble、Gazebo Harmonic 仿真，不连接 RM65B 实机。
6. 可复用模块及其构建、安装和独立启动路径不得依赖 Gazebo、`ros_gz`、`gz_ros2_control`、SDF、仿真 contact/attachment/reset 服务或仿真 world 文件。
7. 稳定的话题、包名和既有仿真入口尽量保持兼容；新增独立公共入口，旧入口改为薄编排层，不复制两套算法。

### 2.1 已实施边界与保留的仿真适配

2026-10-24 按当前源码复核，保留以下职责，不再逐项建设额外隔离框架：

| 内容 | 当前落点 | 审查决定 |
|---|---|---|
| MTC 任务与评分 | `pick_place_mtc`；必需任务参数外置；公共 launch 只接收外部模型/任务配置 | 保留；后端不改变算法源码，沿用加权关节运动量评分 |
| RGB-D/ArUco | `pick_place_perception`；标准图像/内参/TF 输入，只发布位姿与碰撞体观测 | 保留；不创建 PlanningScene 或控制客户端 |
| 场景同步 | `pick_place_scene`；校验、ADD/REMOVE、应用回查、附着保护 | 保留；当前为单对象事务，不宣称完整快照/动态障碍协议 |
| 分段状态与取消 | `pick_place_runtime`；注入式后端、scene revision 检查、停止未确认阻塞 | 保留已接线能力；删除无生产调用的多摘要绑定分支 |
| 已知位姿、观察动作 | `pick_place_demo`；演示坐标、观察运动与示例场景 | 保留为显式输入/演示适配，不要求作为公共算法复用 |
| 抓放编排、接触/附着/复位、故障标记 | `pick_place_sim` | 明确为仿真后端；不再强制提取第二套完整公共任务编排器 |
| 描述与配置 | 无 Gazebo 插件的 URDF/SRDF 与 MoveIt 参数；Gazebo 另行包装 | 保留；当前安装偏移和相机碰撞近似仍是演示限制，实机另验 |

同一 RM65B/夹爪型号的关节名或几何可以保留为设备配置，它们本身不是 Gazebo 依赖。整改重点是算法不读取仿真专有定义，且更换配置即可使用经过校验的设备模型，不要求重写上游描述。

### 2.2 定义、配置和启动的隔离合同

| 分类 | 允许包含 | 禁止混入 |
|---|---|---|
| 公共算法与接口 | RGB-D 几何处理、MTC、候选评估、场景管理、任务状态、标准 ROS 消息 | Gazebo Transport、真值服务、SDF 解析、仿真复位、厂商直接控制调用 |
| 公共场景/任务定义 | 物体 ID、几何、frame、目标语义、支撑面、抓取候选、约束、代价项 | 纹理、仿真实体句柄、摩擦、惯量、控制插件和固定附着锚点 |
| 仿真配置与适配 | world、随机种子、材质/惯量/摩擦、桥接、仿真初值、真值映射、仿真控制参数 | 被公共算法当作必需输入的隐式真值或硬编码安装偏移 |
| 实机/离线观测配置 | RealSense 话题和深度单位、标定版本、实测 TF、模型/工位参数、设备限值 | Gazebo world、仿真 contact、fake JointState 或自动生成的假反馈 |
| 独立公共启动 | 外部模型、显式配置、输入重映射、时钟选择，按需独立启动感知/场景/规划 | 自动拉起 Gazebo、相机硬件、夹爪驱动或硬件执行器 |
| 顶层后端编排 | 仿真、录制回放、未来实机只读/影子规划分别选择后端 | 同时启动多个状态发布者、场景 owner 或设备控制 owner |

公共配置只保存共享默认值；仿真与实机配置各自覆盖它，不互相 include。迁移模式缺少关键标定/设备参数时显式报错，不回退到演示尺寸、仿真开度或固定世界高度。`use_sim_time` 由顶层统一选择：仿真和带 `/clock` 的回放使用仿真时间，实机数据使用实际 ROS 时间；不得仅因公共算法存在就启动 `/clock`。

公共输入合同还应固定消息类型、frame 语义、深度单位、采集时间、QoS、最小发布频率与超时规则；相机内参/外参和设备配置有可追踪版本。迁移时允许 remap 和参数切换，但不能只对齐话题名就宣布兼容。

模型的物理安装变换与视觉显示必须一致。工具、相机和线缆等规划碰撞几何应按实际配置核验；此前为演示移除的相机碰撞体不能直接视作实机可用模型。公共 attach/detach 表示 PlanningScene 对象归属，不代表 Gazebo 固定关节或实机已经可靠夹持。

经确认的真实质量/惯量可以属于公共机器人动力学模型；需隔离的是仿真专用的物理调参和插件，不能为满足隔离而删去真实模型必需信息。

## 3. 总体数据流

```text
仿真后端：Gazebo RGB-D/关节状态 -- 桥接 --+
回放后端：RGB-D/TF/关节状态录制包 -------+--> 公共感知 --> 目标/障碍物观测
未来实机：相机与唯一状态来源 -- 适配 ----+                     |
                                                            v
已知几何/仿真真值适配器（显式互斥模式） ---------> 公共场景管理
                                                            |
                                              已确认的 PlanningScene/版本
                                                            |
                                                            v
                                                公共 MTC/候选评分
                                                            |
                                                任务状态与执行前校验
                                                            |
                              +-----------------------------+------------------+
                              v                             v                  v
                         Gazebo 执行后端              离线禁止执行      未来实机执行适配
```

公共算法只接触标准 ROS 输入、模型和统一场景，不直接选择 Gazebo 或厂商 API。RViz 是独立观察者，可附加到不同后端；关闭 RViz 不应改变算法结果。未来实机执行适配的实现与接入需遵守实机专项验收，本轮只设计边界并用 mock 验证协议，不连接设备。

### 3.1 场景和执行状态的一致性（按功能阶段逐步实现）

以下是扩展链路的最终约束。阶段 0 只验证现有单对象事务与基本执行后端边界；完整快照、所有权和运行中变化在阶段 3 接入障碍物时验收，多候选摘要在阶段 6 验收。

- 场景管理节点统一接收目标/障碍物观测，校验 ID、frame、几何、时间戳和来源；不同输入源显式互斥，超时不会静默切换成 Gazebo 真值。
- 全局环境几何由场景管理节点写入，应用成功并回查确认后才发布版本和就绪状态。失败的应用不得发布“就绪”；删除/更新必须保留稳定对象 ID 和来源责任。
- MTC `ModifyPlanningScene` 可继续用于私有候选分支的碰撞和附着推演；实际执行时的 attach/detach 经单一受控执行路径提交，并与场景管理协调。禁止感知对已附着对象反复 ADD；不建立第二套与 MTC execution capability 竞争的附着写入路径。
- 区分“本轮目标快照”和“持续环境监测”：规划后可锁定目标快照，但障碍物、数据过期和质量监测持续运行。变化时使候选失效；运行中通过执行后端请求取消/停止并确认结果。仅更新 PlanningScene 本身不会自动停止运动。
- 候选绑定场景版本、目标快照、模型/标定配置和起点状态。执行前重新校验；若执行后端需要重新规划，必须产生新候选和评分，不能执行另一条轨迹仍沿用原候选指标。

## 4. 分阶段实施方案

### 阶段 0：公共算法和消息接口与仿真解耦（2026-10-24 修订）

阶段目标只有一个：公共感知、场景同步、MTC 和已使用的执行协议不读取 Gazebo 专属数据或启动仿真，仿真通过配置与标准 ROS 接口调用同一实现。

### 阶段 2：固定和随机障碍物场景（2026-10-24 静态仿真验收通过）

```yaml
obstacle_min_height: 0.12

```

第一批几何类型：

- 薄墙，例如 `0.04 x 0.40 x 0.25 m`；
- 方块，例如 `0.15 x 0.15 x 0.20 m`；
- 长方体，例如 `0.30 x 0.08 x 0.18 m`；
- 围栏段，用于生成窄通道和绕行场景。

随机生成器属于仿真场景工具，输出公共几何快照，再由两侧适配器转换，禁止 Gazebo 和 MoveIt 各自随机。记录种子、生成器版本、完整生成结果、配置和预期类别，仅记录种子不足以跨版本复现。

常规可行场景先过滤初始碰撞、目标/放置区被占用、越界、重叠及最小间距不足等结构问题，再单独验证规划可行性；几何合法不保证存在完整抓放路径。基准集还应显式保留封路、不可达等预期无解场景，验收结果应为拒绝执行并报告原因，不能强求所有随机场景成功。

### 阶段 3：Gazebo 真值同步 PlanningScene（2026-10-24 静态范围验收通过）

阶段 0 已建立公共场景管理，此阶段只增加仿真专属的真值输入适配器，例如 `gazebo_obstacle_state_sync`，不新增另一套场景写入逻辑：

- 读取 Gazebo 障碍物实体名称和位姿；
- 转换到 `base_link` 或 `world`；
- 发布 `moveit_msgs/msg/CollisionObject`；
- 向公共场景管理提交完整快照或可关联的增删改批次，由其执行 ADD、REMOVE 和更新；
- 为每个障碍物保持稳定 ID，如 `obstacle_wall_00`。

优先沿用已有标准接口，不为静态场景增加新的消息包：

| 接口 | 类型 | 用途 |
|---|---|---|
| `/perception/collision_objects` | `moveit_msgs/msg/CollisionObject` | 感知或显式真值模式的碰撞体输入，供观察和兼容 |
| `/perception/obstacle_status` | `diagnostic_msgs/msg/DiagnosticArray` | 置信度、来源、过期和错误状态 |
| `/perception/scene_revision` | `std_msgs/msg/UInt64` | 场景管理在应用并确认后发布的版本号，命名作为拟议兼容接口 |

`/perception/collision_objects`、`scene_revision` 与 `scene_ready` 已存在；障碍状态诊断仍是可选扩展。先用配置冻结的完整静态几何和稳定 ID，通过现有 ADD/REMOVE 与回查验证，不预建批次消息包。单条 `CollisionObject` 与独立整数不构成原子快照；若后续启用动态多对象更新，再实现关联批次/确认协议。诊断消息和 `plan_ready` 均不能单独作为允许执行的凭据。

全局环境写入、MTC 私有分支和执行 attach/detach 仍遵守 3.1 的职责划分。真值适配器放在仿真包；公共场景管理不链接 Gazebo。真值只在已知几何验证模式作为规划输入，视觉模式仅独立用于误差评估。

验收标准：先以冻结静态快照验证 Gazebo 与 PlanningScene 的位置/尺寸、稳定 ID 和增删确认；再验证更新后拒绝旧轨迹。运行中障碍变化另补场景所有权协调、有效期与取消故障注入后启用，不以现有单对象 revision 宣称具备动态避障。

已交付显式 `obstacle_source:=gazebo_truth`：仿真工具导出 live world，读取已配置稳定 ID 的实际 Box，提交标准观察，由唯一公共 SceneSync 写入并确认。变更只能在执行前静态刷新；没有变化不重写，有变化增加 revision 并拒绝旧候选。初始必需 ID 缺失或真值失败时不就绪；执行后刷新拒绝并要求重启。阶段 4 不得使用此真值输入回填感知输出。

### 阶段 4：RGB-D 障碍物几何感知（2026-10-24 静态几何与回放验收通过）

本阶段的算法、参数校验和公共启动位于独立感知包，仿真与未来 RealSense 共用。第一版优先评估几何方法，对薄墙和块状物体可使用成熟处理链；效果仍需由遮挡、反光、距离和深度噪声测试确认：

```text
Depth Image / PointCloud2
        |
        v
按采集时间查询 TF，转换到 base_link
        |
        v
机器人/夹爪自过滤、工作区裁剪
        |
        v
RANSAC 识别并剔除感知点云中的桌面点
        |
        v
PCL 欧氏聚类或连通区域聚类
        |
        v
AABB/OBB 包围盒拟合
        |
        v
尺寸、体积、高度过滤
        |
        v
发布带时间、来源和质量的几何观测
        |
        v
公共场景管理校验、膨胀并应用 CollisionObject
```

可直接复用的成熟接口和库：

- `depth_image_proc`：深度图和内参转点云；
- `sensor_msgs/Image`、`CameraInfo`、`PointCloud2`；
- PCL 平面分割和聚类；
- MoveIt PlanningScene 和 Occupancy Map Monitor；
- OctoMap：需要体素化未知空间时使用。

第一版建议使用粗粒度 Box；如启用 OctoMap，应明确它与显式碰撞盒的职责，避免同一目标或障碍物重复占据。桌面点从分割输入剔除不代表删除规划中的支撑面；被抓取目标要单独标识和屏蔽，避免附着后仍被障碍物点云挡住。

迁移前必须校验以下数据条件，不能以话题名称相同作为兼容证据：

- `16UC1` / `32FC1` 深度编码及单位按实际驱动输出配置，缺失值、范围和无效像素有明确处理。
- 深度与彩色图的配准方式、分辨率、CameraInfo 和 optical frame 一致；未对齐的深度不能直接按彩色像素取值。
- RGB/Depth 按采集时间配对，TF 使用采集时间查询，腕部运动时不能用最新 TF 替代；记录延迟、容差及丢帧。
- 自过滤使用同时间的机器人状态和工具/相机碰撞模型，避免把夹爪识别成障碍物，或误删近旁真实障碍物。
- 每个包围盒标明观测完整性与不确定度；单视角包围盒只包围已见点，通常低估真实外形，不能宣称是完整障碍物边界。

对遮挡区域不能作“没有障碍物”处理，必要时增加观察位、多视角采集和未知区域保守禁入体。观察动作本身也必须通过当前保守场景规划，不能为了获取点云先穿过未知空间。验收应包含无 Gazebo 的 RGB-D 回放和有 Gazebo 的独立真值误差评估，两者使用同一公共算法。

本次公共实现使用 NumPy/SciPy 完成深度解码、RANSAC、欧氏聚类和已见 AABB，读取外部 URDF/相机碰撞模型及采集时刻 TF，目标单独屏蔽。未知体素保留为禁入盒；已见盒明确不完整。标准 compound BOX 通过唯一 SceneSync 一次确认，默认单盒行为兼容；不新增批次消息或回放框架。一次显式静态 capture 后冻结，使用 ROS/steady 双时钟过期，过期使场景未就绪；换场景需重启。

实际 Gazebo 单墙图像及扩大视野自过滤分别验收；关闭仿真后的原生图像录包回放通过。标准视野外沿差异约 1.083 mm；偏侧视野看到的墙厚仅约 3.05 mm（真值 40 mm），完整外沿检验失败，保留该失败并以已见表面误差/未知体覆盖分别评估。两者未知几何均覆盖全部 343 个墙体内采样点，不将采样结果外推为连续安全证明。扩大视野过滤 307 个机器人点，仍保留基座附近残余和网格附近保守禁入；不能为了获得有解路径直接清空这些区域。

录包是静止仿真图像、实际关节状态、采集时刻 TF 样本及单独已知目标；不是硬件或连续运动录制。仅视觉场景的 MTC/执行接线、深度/外参/时间/跟踪误差、低质量与运行中失效取消进入阶段 5；多视角或移动腕部只有在实际启用时补相应数据和观察路径证据。

### 阶段 5：障碍物误差与安全膨胀（2026-10-25 固定附着仿真有界验收通过）

感知尺寸不能直接作为碰撞尺寸。最终规划盒体应包含：

```text
测量尺寸
+ 深度误差
+ 相机外参误差
+ 时间同步误差
+ 机器人跟踪误差
+ 安全余量
```

误差模型和膨胀量应配置化，区分有依据的误差边界与经验余量；尺寸或方向存在歧义时使用保守覆盖，不能仅给已见点盒体增加一个未经验证的小常数。仿真参数不得直接作为实机批准值，未来实机需结合标定、测量和跟踪数据重新确认。

现有 MTC 已有 `planning_candidates` 多解生成和加权关节运动量评分；本阶段在此基础上扩展抓取/运输多样性、间隙评价与候选归档，不把已有多解能力描述为从零新增。当前已配置的候选来源包括：

- 正面、左侧、右侧抓取姿态；
- 不同夹爪偏航角和预抓取距离；
- 不同运输中间 waypoint；
- 不同放置接近方向和撤退方向；
- 不同 OMPL 规划器、重复采样和规划时间预算。

Approach、Lift、Place、Retreat 继续优先使用 Cartesian/Pilz LIN，并验证碰撞、关节限位及时间参数化；Transport 使用 OMPL。优先复用当前版本的 MTC 多解机制，必要时使用 `Alternatives` 或多次任务构造。随机种子只通过当前 OMPL/MoveIt 版本实际支持的接口设置和记录，不假设存在通用的逐请求种子参数。多次采样不保证路径拓扑不同，应按抓取方向、经过区域和路径相似度统计有效多样性。

每条候选必须先满足硬约束：完整任务可解、碰撞和最小间隙达标、关节及速度/加速度不越限、夹爪/相机不碰撞工作台、起点与当前反馈一致、PlanningScene 及模型/标定版本未变化。满足后再按代价排序，例如：

```text
总代价 = Σ 权重_i × 归一化代价_i
代价项 = 路径长度、关节运动量、规划耗时、间隙余量、路径偏差、姿态变化
```

明确各项单位、归一化基准、权重及越界规则；总代价越低越优。间隙和碰撞硬门槛不能被其他低代价抵消。完整任务的抓取、运输及放置阶段均参与校验，不能只比较自由空间段。

优先复用已有诊断输出，避免为每个字段增加话题：

| 已有接口 | 用途 |
|---|---|
| `/pick_place/solution` | 选中任务解与既有观察工具兼容 |
| `/pick_place/planning_metrics` | 现有关节运动量评分、候选编号与选中索引；需要时扩展诊断内容 |
| `/pick_place/candidate_scene_revision` | 当前候选绑定的进程内场景 revision |

候选比较先写入一次运行的结构化归档：候选 ID、目标、场景/配置及起点、评分、最小间隙和失败原因。只有实际消费者需要时再新增消息接口，不复制 `/perception/scene_revision`。模型/标定/起点绑定在候选生产者与执行消费者实际接线时实现，避免重复本次已删除的“只有 schema 和自测”的框架。

执行前重新核对绑定条件和感知新鲜度；条件变化时拒绝旧候选，需重规划则生成新 ID 并重新评分。执行器不能静默重规划后仍报告执行了原候选。评分与比较属于公共模块，Gazebo 最终位姿和接触真值仅由仿真评估器附加。

## 6. 全链路验收顺序

先确认阶段 0 已通过且本次变更未破坏相关隔离 gate，再按所处扩展阶段运行对应检查。尚未实现的视觉/多候选阶段标记为待验，不用真值或单条解冒充通过。扩展完成后的仿真全链路顺序如下：

1. 选择仿真配置并启动唯一的状态/控制来源、Gazebo、MoveIt 与公共模块；RViz 可选。
2. 生成工作台和障碍物，记录种子与完整场景；选择已知几何或视觉输入，禁止混用真值兜底。
3. 独立评估 Gazebo 真值与配置、TF 和几何；视觉模式不向规划补入真值。
4. 检查 RGB、Depth、CameraInfo、PointCloud2、TF 和时间戳。
5. 检查 `/object_pose` 和 `/place_pose`。
6. 公共场景管理提交完整环境更新，确认应用和查询结果后发布就绪版本。
7. 生成多个 MTC 候选并归档；需要时在 RViz 显示。
8. 检查完整任务硬约束、场景/配置版本、起点及感知新鲜度。
9. 选择总代价最低的有效候选；执行前再次校验绑定条件。
10. 通过仿真后端先验收固定附着执行，再单独验收真实接触模式；两者使用同一公共任务接口。
11. 验证抓取、搬运、放置、撤退、回 Home 和复位。
12. 保存场景快照、种子、版本、位姿、候选评分、取消/停止结果和 Gazebo 最终物体位姿，并复测相关隔离 gate。

规划成功不能代替执行成功；RViz 轨迹动画不能代替 Gazebo 关节反馈；视觉检测成功不能代替障碍物场景同步成功。

## 7. 失败分类与处理边界

| 失败类别 | 证据 | 处理范围 |
|---|---|---|
| 隔离验收失败 | 公共依赖 Gazebo、独立入口拉起仿真、配置静默回退 | 留在阶段 0 修正边界，不开始阶段 1—6；扩展期间发现则暂停扩展并修复 |
| 场景生成失败 | 障碍物重叠、越界、初始碰撞 | 修正生成器和种子，不进入规划 |
| 感知失败 | 点云为空、桌面分割失败、障碍物过期 | 阻止执行；运行中请求停止并确认，重新观察，不切换真值兜底 |
| 场景同步失败 | 应用失败、回查不符、版本未确认 | 不发布就绪、不规划/执行；检查公共管理和对应输入适配器 |
| 规划失败 | 碰撞、IK 失败、无可行候选 | 调整候选姿态或规划参数，保留失败记录 |
| 执行失败 | 控制器超时、关节反馈不跟随 | 检查 Gazebo 控制器和反馈，不归因于感知 |
| 抓取失败 | 接触丢失、物体滑落 | 单独检查夹爪、摩擦、质量和速度 |
| 场景过期 | 规划后障碍物移动或相关版本改变 | 拒绝旧解；运行中经后端取消/停止并确认，再重新感知规划 |
| 停止未确认 | 取消超时、控制反馈持续运动 | 保持故障状态，不执行下一段或自动复位，保留后端诊断 |

### 8.1 配置与启动入口交付

公共任务/感知配置与三个独立入口已经交付。其余配置随对应数据来源和设备建设，不再全部作为阶段 0 出口：

- 设备/工位配置：经确认的模型、工具/相机安装、夹爪限值与标定标识；仿真与未来实机分别选择实例，不能把当前演示外参默认为实测值。
- 仿真配置/启动：显式选定 world、传感器桥接、时钟、真值模式与仿真执行后端，调用公共入口。
- 阶段 4 离线回放配置/启动：仅启动所需公共节点和录制输入，可附加 RViz；不含仿真或硬件驱动，不加载执行器。
- 实机迁移专项的只读/影子规划配置：消费外部相机与官方状态来源，加载经确认模型；缺标定/限值即拒绝就绪。本轮不实现或启用实机控制驱动。
- 独立公共入口：感知、场景、仅规划按需启动，外部提供状态和依赖；无输入明确等待，无执行后端禁止动作。公共 runtime 是库，暂不为它添加独立编排节点；既有仿真入口继续保留。

### 8.2 后续新增内容的准入规则

阶段 1—6 的每个变更提交验收前，必须逐项回答：

1. 哪些是公共算法/定义，哪些是仿真适配？新增依赖是否遵守“后端依赖公共、公共不依赖后端”？构建、安装、launch 导入均需检查。
2. 可迁移内容能否通过配置与标准输入在无 Gazebo 环境独立运行？是否新增隐藏的演示参数、真值回退或重复状态发布者？
3. 场景写入者、执行 owner、对象 ID/frame、单位、时间戳、标定版本与候选失效规则是否明确？是否会覆盖附着对象？
4. 无执行后端、数据过期、场景变化和取消失败时，是否保持拒绝执行/故障状态？新增动作是否通过同一后端接口？
