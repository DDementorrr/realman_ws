# 2026-10-23 RM65B 阶段 0 ROS 执行后端接线与取消验证

> 历史执行记录：下文结论对应当时的原 G0 门禁。2026-10-24 已按用户要求审查精简并修订验收范围，当前结论见[范围审查与验收](2026-10-24-RM65B阶段0范围审查精简与验收.md)；未将原缺项改记为通过。

## 结论

本次将 backend-neutral `ExecutionCoordinator` 接入仿真执行入口，并新增基于 Humble `rclpy` action 的 MoveIt 后端适配器。每个 MTC 分段的后续动作必须等待 action 终态成功；取消只有在 `CancelGoal` 响应包含当前 goal 且最终结果状态为 `STATUS_CANCELED` 后才算确认。取消被拒绝、反馈异常或超时都会阻止后续分段，并将任务故障锁存到执行节点；锁存后 `/pick_place/execute` 和 `/pick_place/reset` 均拒绝继续。

正在执行时若 SceneSync revision 变化或 `scene_ready` 撤销，执行器请求 action 取消。另新增 `/pick_place/cancel` 服务用于请求当前 action 取消。一次任务固定复制 solution、description、抓取/放置目标与 candidate revision，避免运行期间订阅回调将多段执行切换到新候选。

本次完成 G0-6 的 ROS action 后端接入、取消/故障锁存验证，并通过固定附着仿真抓放与单次 reset 回归；仍不构成阶段 0 通过。公共任务编排与仿真服务调用尚未完成职责拆分，G0-1—G0-5 仍有未完成证据，G0-7 的真实接触和视觉回归也未完成。因此阶段 1—6 不开始。

本次启动并停止了隔离 Gazebo 仿真；未连接 RM65B 实机、未提交或推送；工作区原有暂存与未提交内容保留。

## 实现

- 新增 `src/ros2_adapters/pick_place_sim/scripts/ros_action_backend.py`。它以异步 `send_goal_async`/`get_result_async` 将 `ExecuteTaskSolution` goal 映射为公共 `BackendState`，校验终态和 MoveIt error code，并验证取消响应接受的是当前 goal。服务层接受取消请求不作为停止证据。
- `execute_pick_place.py` 的每个运动分段现在经过公共 `ExecutionCoordinator`；原本绕过协议的直接 action goal 发送已移除。分段超过 180 秒会请求取消，10 秒内没有明确取消终态则 `BLOCKED`。场景失效也请求取消。
- 后端 `ready()` 返回后、发送 action goal 前再次检查 task cancel 标志及 scene revision/ready；检查失败时公共协调器拒绝 goal dispatch。这样 action server 等待期间发生的输入变化不会被送入执行器。
- task motion 开始后遇到执行失败、取消或结果不确定时，执行节点将故障原子写入默认 `~/.ros/pick_place_execution_fault.json`。启动时先检查存储可写性并读取此标记；标记存在、格式错误或存储不可用都会阻止执行/reset。代码未提供清除接口，受监督恢复协议确定前不会自动清除。
- 若任务故障发生后存储设备突然失效，当前进程仍保留内存故障锁存并输出 `CRITICAL`，但标记无法持久写入；进程重启后的恢复判定仍无充分证据，此情况仍是 G0-6 限制。
- task trigger 固定复制候选和目标输入；订阅回调与快照访问由锁保护。没有 revision stream 的既有兼容入口需明确启用 legacy 分支；一旦收到 revision stream，仍要求候选 revision 匹配且 scene ready。
- `pick_place_sim` 补齐直接运行依赖 `action_msgs` 和 `moveit_msgs`，并将 action 适配器安装到执行脚本同目录。公共 `pick_place_runtime` 仍无 ROS、Gazebo、MoveIt 或厂商依赖。
- 固定附着和真实接触 launch 暴露 `execution_fault_latch_file` 参数；默认是 `~/.ros/pick_place_execution_fault.json`，隔离测试可使用临时路径。
- 新增 `src/ros2_adapters/pick_place_sim/scripts/execution_fault_latch.py` 及 `scripts/test_execution_fault_latch.py`、`scripts/check_execution_fault_latch.sh`；新增 `scripts/test_ros_action_backend.py`、`scripts/check_ros_action_backend.sh`、`scripts/test_ros_action_backend_rclpy.py` 和 `scripts/check_ros_action_backend_rclpy.sh`，覆盖故障标记持久性、异步适配器 mock 及进程内真实 ROS action 中间件交互。
- 新增 `scripts/test_pick_place_cancel_runtime.py`，在活动 Gazebo/MTC action 上调用取消服务，验证最终 action status 和故障后 reset gate。

```bash

export ROS_DOMAIN_ID=186 ROS_LOCALHOST_ONLY=1
ros2 launch pick_place_sim execute_pick_place.launch.py \
  headless:=true use_rviz:=false auto_execute:=true \
  execution_fault_latch_file:=/tmp/pick_place_fault_latch_20261023_186.json
python3 scripts/verify_pick_place_stage3.py
```

结果：新 action backend 实际驱动完整 MTC 固定附着抓放；分段依次成功，Gazebo attachment 经过 attach/detach 确认，最终 MoveIt PlanningScene 中对象位于 world 且无 attached object。最终改动版本的 stage3 verifier PASS，Gazebo placement error `0.000 m`；临时故障标记文件未生成。后续单独验证了 reset 和初始场景，没有在 reset 后再次抓放。

验证完成后向 launch 发送 SIGINT。ROS 子进程均退出；Gazebo 8.15.0 在关闭时打印 segmentation fault，launch 将其记录为进程退出错误。它发生在完整执行与 verifier PASS 之后，故不能解释成任务失败，也不能称为干净关闭；这项关闭行为需在后续仿真环境复查。本次没有其他仿真进程残留。
