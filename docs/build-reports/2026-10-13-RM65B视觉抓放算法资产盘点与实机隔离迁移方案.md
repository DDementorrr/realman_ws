# RM65B 腕部视觉抓放：算法资产盘点与实机隔离迁移方案

日期：2026-10-13  
适用工程：Ubuntu 22.04、ROS 2 Humble、Gazebo Harmonic、RM65B + CTM2F110 仿真工作空间  
用途：说明当前 demo 的算法来源和成熟度，制定在工控机侧隔离部署、先观察后控制的迁移流程。

## 1. 结论摘要

当前系统是一个已在 Gazebo 中端到端运行的、单物体直立立柱 Pick & Place 验证样例。它把成熟规划/视觉/消息库与项目自建适配代码组合起来，证明了“腕部 RGB-D → 图像时刻 TF → base_link 下物体位姿 → PlanningScene → MTC 多候选规划 → Gazebo 轨迹执行”的接口链可用。

它不是通用抓取产品，也不等价于实机就绪：目前只识别单个顶面 ArUco ID 0，使用固定尺寸长方体和直立姿态先验；观察姿态、抓取几何、夹持参数和接触模型均按当前仿真工作台调定。相机与夹爪的 Link6 挂载关系还是仿真占位（夹爪 identity mount），实机法兰/工具/相机外参、负载和碰撞模型未标定。当前仓库不含 RM65B 实机控制驱动，且无连接或运动授权。

对于工控机，推荐把本工程作为独立 ROS 2 overlay、独立用户目录或容器中的“只读监控/可视化应用”先部署；不要覆盖 OEM 工程、系统 ROS 安装或厂商服务，不启动第二个硬件驱动。先消费唯一硬件驱动已有的实测关节/状态数据，验证 RViz、相机、TF、目标位姿和 shadow planning。任何发往机械臂或夹爪的命令都必须作为另一个明确批准、独立验收的阶段。

## 2. 当前 demo 做了什么，没做什么

### 2.1 运行链

```text
Gazebo Harmonic wrist RGB-D ── ROS 图像/CameraInfo/深度
                                      │
                                      ▼
                           OpenCV ArUco 检测 + 深度反投影
                                      │ 图像时间戳查询 tf2
                                      ▼
                 PoseStamped(/object_pose, frame=base_link)
                                      │
                    MoveIt PlanningScene ADD / 场景同步
                                      │
                                      ▼
 MTC 构造分阶段任务 → OMPL 自由空间候选 → 六轴加权评分选解
                                      │
                                      ▼
 ROS 2 FollowJointTrajectory 仿真控制器 → Gazebo 反馈
```

任务和各段规划在 MoveIt/MTC 内，视觉节点通过 ROS 话题与 PlanningScene 服务连接；仿真传感器和控制器由单独的描述、launch、Gazebo 模型构成。该边界有利于替换后端，但并不意味着换硬件后无需适配。

### 2.2 当前证据基线

2026-10-12 最终带界面运行记录位于同日 PickPlace 验证报告与全流程教程。该轮视觉误差 7 mm、PlanningScene 同步误差 0；五个完整候选以 `[5,4,3,2,1,1]` 权重评分并选中最小分；实际纯接触抓放放置误差 4 mm，物体直立且返回 Home。带界面搬运期间最大 mimic 偏差约 0.0283 rad，动态反馈 TF 本身误差约零。该结论限于记录中的模型、对象、工作区和参数，不能外推为实机或任意物体性能。

胶垫采用局部 X 方向 ±2 mm 的弹簧支撑刚性垫近似（5000 N/m、19 N·s/m），不是真实橡胶本构。推荐的 1 N·m 主驱动、0.5 ms 仿真步长、夹爪目标 0.55、姿态受限搬运是联合调定参数；没有单因素证明每项分别带来多少改善。胶垫行程偶尔略超名义 2 mm，连杆在受载 GUI 运行仍有约 0.028 rad 偏差。

| CTM2F110 驱动 | 官方 SDK + 自建 ROS 2 adapter | `changingtek_gripper_driver`；默认 `dry_run=true` | 有串口 ROS action/state 包装和 readback 选项，但本仓库只通过 dry-run 构建/行为检查；实物串口、回读准确性、夹爪型号/协议及双端行程未验收。 |
| RM65B API/驱动/状态采集 | 厂商上游，不在当前自建实机链中 | 上游锁定 `realman_ros2` commit；含 `rm_driver`/`rm_control` | 可按厂商该版本文档与设备型号评估。仓库自身不启动该驱动、不含实机 `ros2_control` 硬件插件，也未验证用户当前直接 API 的调用方式。 |

### 3.1 哪些是“演示性的最简构建”

1. 一个预定义位置、尺寸和方向的桌面立柱，一个固定放置位；无工作空间扫描。
2. ArUco ID 0（DICT_4X4_50）贴在已知尺寸物体顶面；对象 orientation 设为单位四元数，物体中心 Z 由已知高度减半得到。该实现测的是“已知直立长方体的中心位置”，不是任意物体 6D pose。
3. 观察位固定在 `base_link`，张开夹爪后由 MoveGroup 运动到观察位；定位成功后等待 MTC，plan_ready 后冻结视觉 pose。本 demo 不执行连续 visual servo，也不在运动中根据新图像闭环纠偏。
4. 接触参数面向当前 Bullet 仿真调试；柔性只用线性弹簧/阻尼近似，没有橡胶应力应变、速率依赖、滞回或材料温度效应。
5. 本轮评分只统计规划消息中六个机械臂关节各轨迹点的加权绝对角度增量，未对耗时、奇异性、碰撞裕度、速度/加速度、能耗、夹持稳定性作联合评分。

这些简化适合教学、链路集成和回归，不应伪装成高泛化能力。

### 3.2 哪些是自主构建但较标准、较好迁移

- ROS 分层：感知发布 `/object_pose`；任务规划消费物体/放置位姿；执行通过标准 trajectory action；状态只由实际关节/设备反馈提供。
- 图像时刻 TF 转换、清晰定义 frame_id、PlanningScene 碰撞对象更新；这些算法可迁移，但实现需增加数据质量与异常保护。
- MTC 用标准 stage 表达 task，而不是将 perception、task、simulation 写成一个节点。上层任务定义可保持，只替换状态/执行 backend。
- 实测 JointState 进入 robot_state_publisher，区分“实际状态可视化”和“理想 mimic 模型”。实机反馈来源必须选唯一可信驱动，不能再叠加仿真状态发布者。
- 每阶段独立验证以及 trajectory/source 复核。流程方法可迁移，具体验收门限和真值接口须重新定义。

## 4. 对实机可直接迁移的判断

“直接迁移”指复用源代码或接口后，经设备/型号参数确认能运行；不代表直接连接后即可下发运动。

| 资产 | 建议处理 | 实机前置条件 |
|---|---|---|
| `/object_pose`、`/place_pose`、`PoseStamped`、frame 约定 | 保留消息契约 | `base_link` 必须指向实机底座基准；统一方向、单位、stamp、时钟和坐标约定。 |
| OpenCV ArUco 检测流程 | 复用算法，重做相机 driver 输入 adapter | 实机相机内参、RGB/depth optical frame、深度对齐、外参与实测距离校验；考虑 RealSense ROS wrapper 的实际 topic/QoS。 |
| tf2 动态变换查询 | 复用机制，重建实机 TF | 唯一发布 `joint_states` 的实机反馈；正确 URDF；实测 flange/TCP/camera transform；禁止用仿真时间。 |
| MTC task stages 和候选评分 | 可移植源代码，先只规划不执行 | 确认实际 RM65B 型号、关节名和正方向、软限位、IK、碰撞几何、夹爪工具模型及起始状态；重新验证工作空间和放置位。 |
| MoveIt 配置 | 仅作为初始模板 | 现有执行 action/control interface 必须由厂商接口或经过验证的 hardware adapter 提供；仿真 controllers YAML 不可复用为实机控制端。 |
| `wrist_camera_mount xyz=0 0 0.10` | 仅目标设计值 | 从实际 Link6/TCP 坐标定义量起支架；做 eye-in-hand 外参标定和 TF 验证。相机与夹爪 identity mount 均不可当作真实测量。 |
| `pick_place_sim`、Gazebo SDF、`gz_ros2_control`、Gazebo attachment/contact | 不迁移进实机运行链 | 留作仿真/离线训练与回归环境。 |
| GUI 上的关节/目标/图像显示 | 可移植 observer 部分 | 显示数据必须来自实机 feedback/camera，而不是 MoveIt planned state 或 fake JointState。 |
| 固定夹爪参数/碰撞/抓取偏移 | 不可照搬 | 依据实机夹爪型号、接口、垫片尺寸、对象质量、工具中心、低速验证重新标定。 |

建议先将真实接口包在统一边界后，再切换 backend：

```text
perception → ObjectPoseProvider(/object_pose)
task/MTC  → JointStateProvider + PlanningScene + MotionExecutor(action)
                                  ├─ sim backend（现有 Gazebo）
                                  └─ real backend（厂商 API/driver adapter，单独批准）
```

上层可共用任务逻辑；硬件执行 adapter、硬件安全状态、故障恢复和参数不应与仿真 adapter 混用。

## 5. 工控机工程迁移与隔离策略

### 5.1 迁移前先盘点，不先安装

由设备负责人确认并记录：Ubuntu/内核/CPU 架构、ROS 发行版、厂商软件版本和启动方式、当前工程路径、服务/udev 规则、网络接口和 IP、RM65B 型号与固件、夹爪具体型号、相机型号、维护窗口、备份恢复方式。只读记录 `env | sort`、已安装 ROS 包、当前 ROS nodes/topics/services/actions、launch 文件来源、设备权限、端口占用和进程，不输出账号密钥。

确认控制入口到底是用户直接调用的瑞尔曼 API、厂商 ROS `rm_driver`/`rm_control`，还是工控机自有服务。只选择一个负责写硬件命令的 owner。不要因为仓库上游存在厂商 ROS 源码，就默认它与现场实际控制服务兼容或可并行启动。

### 5.2 隔离等级（由低风险到高风险）

| 模式 | 部署方式 | 是否允许发硬件命令 |
|---|---|---|
| A：离线构建 | 另一台相同架构 Ubuntu，或单独 Docker/Podman 镜像；无设备映射、无机器人网路由 | 否 |
| B：工控机只读 observer | 独立用户目录和独立 `~/rm65b_observer_ws`（各自 build/install/log）；source 已有 ROS underlay 后只加 observer overlay。优先 DDS 只订阅现有 driver 状态与相机流 | 否；不启动 hardware driver/action server |
| C：影子规划 | observer 另外启动只读 MoveIt planning/display 节点，使用实测状态、真实模型和实测场景；规划结果只显示/记录，不接 controller manager | 否；关闭执行入口或网络 ACL 阻断写控制通道 |
| D：受监督执行 | 独立、明确批准的 real execution adapter 对接唯一硬件 owner；单步低速测试并有现场人员/急停 | 是，但另立安全审查、权限和验收，不属于本次迁移报告的已验证范围 |

优先使用 A/B/C。ROS_DOMAIN_ID、namespace 只能隔离 ROS graph 发现，**不能**隔离直接 TCP/UDP/API 到机械臂、串口设备、共享参数文件或系统服务；不要把它当作安全互锁。容器只有在不映射 `/dev`、不连控制网时才算离线隔离；若要读相机/机器人网，仍需逐项设置网络只读访问策略。

不要覆盖 `/opt/ros`、厂商目录、系统 Python、现有 shell 初始化、systemd 服务、udev 或设备网络配置。创建并备份独立仓库副本，在独立 workspace 编译；不要把本仿真的绝对路径 `source_pick_place_env.sh` 加到工控机全局 shell。当前启动脚本会加载本地 `gz_ros2_control` 和 MTC 私有前缀，不能直接用于只读实机环境。

### 5.3 分阶段迁移流程及 gate

| Gate | 工作 | 通过条件 | 禁止事项 |
|---|---|---|---|
| 0. 资产冻结 | 记录厂商工程版本、备份、网络/ROS 图、接口 owner、安全流程；拷贝本仓库到独立目录 | 可恢复备份且现场负责人确认连接/停机边界 | 不改现场软件和网络、不连臂 |
| 1. 离线适配 | 在同架构独立环境确认 ROS distro、依赖和厂商接口版本；仅编译描述/observer/验证包 | 干净构建、无 Gazebo 依赖泄漏到 observer 入口、无硬件设备权限 | 不将 Humble 叠加到未知厂商 ROS distro，不直接 apt upgrade |
| 2. 只读 ROS 接入 | 查询现有实际 JointState、状态/报警、driver health、camera topic；观察节点只订阅 | 实测反馈更新、frame/时间戳正确，无重复 JointState publisher，无 action client 写请求 | 不启动第二套 `rm_driver`，不发布 trajectory |
| 3. 显示与模型核对 | RViz 显示实测关节；对比视觉窗口、工具、底座和机械臂；先核模型和坐标轴 | 所有关节方向/零位、TCP、夹爪和相机外参经过静态测量验证 | 不用 MoveIt planned state 假装实测 state，不只凭 RViz 判断真机位置 |
| 4. 相机/感知 shadow | 接入 RealSense 或当前相机 ROS driver；采 CameraInfo、对齐 depth；标定 eye-in-hand；只发布诊断目标 | 静止多点对比独立量测，误差和重复性达项目门限；错误 frame/丢帧时 fail-closed | 不让 shadow pose 自动进入硬件执行端 |
| 5. MTC shadow planning | 用真实关节反馈为 start state、实测工作区障碍构造场景，生成 3–5 个方案并可视化；不连接 controller manager | IK、关节范围、碰撞、速度/加速度、路径时间、评分项人工审查；重启可复现 | 不能将仿真候选分数视作真实安全/可达证明 |
| 6. 控制 adapter bench | 确认厂家 API 对应 action 语义、单位、速度、急停/停止、超时、取消和回读。先在台架/仿真 API 或空载隔离测试 | 独立代码评审、限速和安全 stop 经过验证，反馈闭环真实 | 禁止未经授权连接并运动；不得双 driver 同时拥有写权限 |
| 7. 受监督实机基本动作 | 设备负责人完成安全检查，使用厂商批准的模式，从低风险单段/小范围开始，现场急停可达 | 每步检查 driver 状态、实测反馈、工具/环境间隙、停止能力；异常立即停机复盘 | 不直接运行本 demo 的整套抓放，不从自动执行或视觉触发开始 |
| 8. 受控任务扩展 | 经过独立单步验收后才逐步合并 perception、planning、execution | 每项有明确版本、责任人、记录、复位/故障策略和风险复核 | 仿真阶段通过不自动授权这一阶段 |

## 6. “完美隔离”能否做到？

可以把文件、依赖、构建产物、launch 和 ROS 图尽可能隔离，避免破坏 OEM 工程；但若同一工控机通过物理网线/串口连接机器人，无法仅靠 ROS namespace 声称“完美隔离”。任何具备可达硬件 API 的进程在技术上都可能写设备。因此隔离要同时覆盖：

1. **文件/依赖**：独立仓库副本、workspace、`build/install/log`、用户和容器镜像；不覆盖厂商软件和系统环境。
2. **ROS graph**：独立 domain/namespace，显示节点只订阅；启动后检查 publisher/subscriber/action server 清单。
3. **硬件写路径**：observer 不创建控制 action server/client，不映射串口，不允许到控制端口出站；尽可能由防火墙/交换机 ACL 控制只读状态流。若厂商状态和命令共用同一个 TCP 连接，则需评估协议/driver 权限，ROS graph 隔离不能替代网络访问控制。
4. **状态一致性**：只保留一个实机状态来源。运行 `ros2 topic info -v /joint_states` 检查是否有且仅有预期 publisher；仿真和实机模型/状态发布不得同时出现在 observer 图中。
5. **执行能力**：只读配置里不启动 execution manager/controller manager，不提供 `/pick_place/execute` 到硬件的桥接；以后引入控制时采用显式独立 launch、配置和审批流程。

因此，最安全且不破坏现有工程的第一步是 **工控机只读 observer + RViz/相机/话题验证**。它可以与 OEM 控制进程并存的前提，是 ROS 发行版/通信兼容、资源足够且状态接口不争用；这需先查现场配置，不能预先承诺所有工控机都兼容。独立 SSD/第二台电脑/隔离容器可进一步降低软件环境影响。

## 7. 实机验证接口建议

在接入前，先用 `ros2 node list`、`ros2 topic list -t`、`ros2 topic info -v <topic>`、`ros2 action list -t`、`ros2 service list -t` 建立现有图的基线。只读模式建议记录：

| 观测项 | 验证重点 |
|---|---|
| JointState | 实际 position/velocity、单位 rad、header stamp、六关节完整性、唯一 publisher、驱动状态与读回延迟 |
| TF | `base_link → link6 → tool0/TCP → camera optical frame` 单一连通；静态尺量和已知关节角时核位置/朝向；不混入 sim time |
| Camera | RGB、depth、CameraInfo topic/encoding/QoS、标定内参、depth alignment、时间戳、丢帧；`rqt_image_view` 只观察，不将它当作定位精度证明 |
| Object pose | `PoseStamped.header.frame_id=base_link`，timestamp 对应图像采集时刻；与独立量具/标定板实测比较，记录误差、重复性、失效/过期状态 |
| PlanningScene | 桌面/障碍/机器人/夹爪尺寸一致；只读查询规划场景，不从 Gazebo 真值获取实机目标 |
| Shadow plan | planned joint trajectory 与实测 start state 对齐，离线检查限位、碰撞和各段姿态；没有 hardware trajectory action server |
| Hardware health | 厂商 API/driver 报警、模式、使能、速度比例、急停状态按设备授权只读采集；任何告警必须令上层阻止执行 |

## 8. 迁移实施前需向现场确认的项目

- 工控机操作系统、架构、ROS 版本、是否由厂商定制镜像管理；是否允许 Docker/第二用户/新 workspace。
- RM65B 的具体后缀/固件、控制柜/API 版本、IP 与读状态/写控制端口、用户当前使用的 API SDK 和进程生命周期。
- 是否已有 ROS 2 `/joint_states`、报警/运行模式 topic，还是仅 API；是否已有 `rm_driver`/`rm_control`，其版本是否与现场 SDK 一致。
- 夹爪实际型号（CTM2F110、CTM2F110E 或其他）、供电/串口/控制板固件、SDK/标定换算和 position readback 支持。
- RGB-D 相机型号、驱动、内外参、安装支架/Link6/TCP 的测量方法与安全线缆布置。
- 厂家/实验室实机操作 SOP：急停、使能、手动/自动模式、速度限值、工作空间、人员隔离、负载、工具、碰撞停止和授权人。
- 现场是否批准 observer 连入控制网；是否能通过 VLAN/ACL 仅开放 telemetry；是否可在 robot-disconnected 条件下先验证 GUI。
