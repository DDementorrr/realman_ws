# RM65B 实机测试与标定清单

更新：2026-10-28。适用当前 RM65B、末端夹爪、腕部相机及 MoveIt/感知/抓放工程。

这是一份现场执行顺序和记录清单，不是实机启动脚本。本轮没有连接或运动设备。现场状态见[本轮准备记录](../experiments/2026-10-28-RM65B实机准备状态与验收记录.md)；详细停止、安全及性能方法沿用[实机验证与标定规划](../build-reports/2026-10-20-RM65B实机验证与标定规划.md)。

## 当前起点

| 内容 | 当前能确认的程度 | 下一步 |
| --- | --- | --- |
| 相机手眼标定 | 用户报告“应该已完成”；本仓库未核验现场参数、原始采样或独立误差 | 先备份并复核，不默认重做，也不直接记为验收通过 |
| 夹爪 | 用户报告可能尚未启用；现有适配默认 dry-run，未获得硬件运行证据 | 优先确认实际型号/协议并独立测试 |
| 机械臂实机执行 | 有厂商来源和公共执行契约，但现场控制 owner、action 映射、停止回读未在本仓库验收 | 先只读，再审查执行接口，最后做单段动作 |
| 模型/TCP | 法兰到夹爪安装变换仍是仿真假设，TCP 在夹爪基座局部 Z 偏移 0.14 m | 测量实际安装、标定 TCP、同步厂家与 MoveIt 定义 |
| 前端/算法 | 仿真原生规划、限速、IK、拖动和低速执行已有测试；位置—姿态地图仍是方案 | 复用交互和算法；不继承仿真坐标、速度或硬件验收结论 |

先完成下面 1—6，再做 7—10。每项只记录一次“通过/失败/未做”和证据；没有证据就保留未验，不再额外建立一套验收框架。

## 依次进行的十项主线

| 顺序 | 测试/标定 | 具体做什么 | 完成判据与保存内容 |
| --- | --- | --- | --- |
| 1 | 设备与控制基线 | 记录机械臂、控制器、固件、夹爪完整型号、相机序列号；备份厂家配置和已有标定；确认工具固定、线缆、现场停止/复位流程及唯一写设备 owner。装有工具时，首次运动前就应配置经确认的工具负载和适用 TCP；不能等到最后才考虑负载 | 一份版本/配置清单；明确哪些程序只读、哪个程序能发动作；测试速度和误差阈值先按实际手册与项目要求填写 |
| 2 | 真实反馈与时钟 | 从现有厂家驱动只读查看关节角、模式、使能、报警、厂家 TCP；对照示教器，确认 rad/deg、m/mm、关节名、轴向和时间戳。实机 ROS 使用真实时钟；静止状态先验证，不启动本工程运动入口 | 多组静止状态下示教器与 ROS 对应一致；知道每个数值是实测还是命令回显；反馈丢失/过期可被识别 |
| 3 | 夹爪单独启用 | 机械臂静止，先按对应型号厂家工具确认通信，再接 ROS 包装；检查两个执行器、开合方向、端点、多点开度、回读、取消和失联行为。先空爪，再在有承托的台架上夹标准块/轻物并释放 | 记录命令值—实测开度曲线、回差、两侧一致性和故障状态；“命令发送成功”与“实际到位/夹住物体”分开判断；未通过前不进行提物 |
| 4 | 基座、工具、负载与 TCP | 核对实际安装方向和 `world/base_link`；测量法兰到工具安装变换，按匹配控制器的厂家流程做多姿态 TCP 标定和轴向校验；称量夹爪、相机、支架和随动线缆，配置工具质量/重心，核对惯量要求 | 固定基准点多姿态验证 TCP，不仅看拟合残差；厂家工具号/工作坐标系与 MoveIt 一致；保存变换、负载、适用夹爪状态和工具版本 |
| 5 | 相机链与已有手眼复核 | 检查 RGB/Depth/CameraInfo、分辨率、深度单位和对齐模式；导出已有手眼矩阵，确认 eye-in-hand、变换方向以及父 frame 是 flange 还是 tool；使用未参与拟合的靶点/腕姿验证 base 系点位一致性 | 保存内参/手眼文件、采样与保留验证数据；统计跨姿态偏差、位置/姿态误差和时间偏差。只有复核不通过才定位原因并重标定 |
| 6 | 工作台、场景与感知 | 测量桌面、夹具、禁入区和放置区；核对机械臂/夹爪/相机/线缆碰撞体；先已知固定靶，再不同位置/高度的物体，检查图像定位到 base 的结果。补上实际工具/工件尺寸及定位不确定性 | 视觉坐标与独立量测在预先定义的门限内；PlanningScene 与实物对应；遮挡、失去目标、错误 frame、过期 TF/图像必须标无效，不能沿用旧点继续抓 |
| 7 | 真实状态下只规划 | 用实测关节作起点，使用量测场景；保持实机执行通道断开，仅做 IK/FK、关节/姿态目标、碰撞、轨迹速度与加速度检查；对多个 IK 分支和当前姿态连续性作检查 | 原生 RViz 的目标、关节解、轨迹和实际坐标一致；请求变化使旧计划失效；影子模式不能意外发到设备；规划成功只记为规划通过 |
| 8 | 执行接口与空载单段 | 先在无运动的测试环境核对 action/API、关节顺序、单位、时间参数、拒绝/取消/结果语义。之后由现场操作员按厂家批准的流程执行小范围单关节，再做固定姿态短段 TCP 动作；验证暂停、取消、完成和停止后反馈 | 唯一控制 owner；记录轨迹命令、实测关节/TCP、跟踪误差、结束状态和停止行为；软件返回取消不能代替设备停止确认；现场故障试验按厂家规定进行 |
| 9 | 已知位置单步抓放 | 先不用图像：用量测目标，分开执行预抓取、接近、闭爪、确认夹持、小幅抬升、搬运、放下、松爪。每段观察后才推进下一段；物体先轻质且有承托/防坠安排 | 抓持成功有真实证据；附着/分离状态与实物一致；放下后确认物体稳定再松开；任何段失败不得自动跳到下一段 |
| 10 | 视觉与完整任务 | 已知位姿任务稳定后，替换为真实视觉目标；先无遮挡静态场景，随后加入一个已测障碍物，再启用候选评分与完整 MTC 任务；最后才验证有限次数重复与异常恢复 | 每轮绑定真实起点、标定版本、场景版本、候选与实际执行轨迹；记录成功率、误差、用时、失败原因和恢复步骤；未覆盖的动态场景不作已通过结论 |

说明：第 4、5 项中的腕姿变化可沿用现场已验证的厂家示教操作，不要求提前启用本工程执行后端。第 8 项只在前面的模型、现场流程及接口验证满足条件后进行。

## 最值得优先核对的工程细节

### A. 夹爪当前不能直接当作已就绪设备

实际型号必须先确认是 CTM2F110、CTM2F110E 还是其他型号，再核对电气接口、供电、串口参数和 SDK；不能因为名称相近就套用同一动作范围。当前[夹爪适配说明](../../src/crt_ctm2f110_gripper_visualization/changingtek_gripper_driver/README.md)和源码说明了以下边界：

- 默认 `dry_run=true`；`readback=false` 时是命令回显，不能作为实际到位证据。
- 适配沿用 SDK 的位置换算 `1700 - 700 × joint_position`。这是 SDK/模型映射，不是夹爪开度 mm，也不是抓取力 N；需要在实际型号上独立量测。
- 当前回读将两个执行器换算位置取平均。一侧异常可能被平均值掩盖，单侧状态应分别检查。
- **回读失败会保留旧值，而发布的 JointState 时间戳仍更新。** 不能仅凭消息持续到达就判定状态新鲜。进入自动抓放前，需要明确的读回有效性/最近成功采样时间和超时拒绝策略。
- **当前 action 返回成功以发送完目标点为主，没有实测到位条件；取消路径返回 canceled，但没有独立确认夹爪电机已停。** 这两项必须在硬件执行适配中验证或补足，不能把 action 状态当成持物/停止确认。
- 当前工程没有已验收的标定抓取力接口。若没有实际力传感器或厂家已定义并验证的反馈，不记录“夹持力 N 已通过”；电流、effort、位置、接触与实际夹持力应分别记录。

机械臂与夹爪可以有各自状态源，但每个关节只能有一个可信 owner。必要时先发布独立状态 topic，再合并；不要把所有 `/joint_states` 发布者一概视为重复，也不要让 Gazebo/fake feedback 混入实机来源。

### B. TCP、手眼与相机内参是不同标定

| 项目 | 描述什么 | 何时需要重验/更新 |
| --- | --- | --- |
| 相机内参/深度 | 像素、深度到相机三维点 | 分辨率、流配置、对齐方式、固件或相机改变时核对；通过实测决定是否重标定 |
| 手眼外参 | 相机相对法兰/工具的刚性安装 | 支架/相机安装改变后重验；先确认保存的父 frame 与变换方向 |
| 工具安装与 TCP | 法兰、夹爪和抓取参考点关系 | 工具、安装件、指尖/垫片或参考夹爪状态改变后重验 |
| `world/base_link` 与工位 | 机器人在桌面/工位中的位置 | 移动底座、工作台或工位基准后重验 |

如果外参保存的是 flange→camera，单纯重新定义 TCP 不会改变相机的物理安装变换，但 TF 链需要保持一致。如果保存的是 tool→camera，工具 frame 定义改变后必须重新表达这段变换，不能原样套用。先验证整条坐标链，再判断是否需要重做手眼。

复核已有手眼时，建议先做“静止靶点＋不同腕姿”的独立检查：同一个固定靶点在 base 下不应随腕姿明显漂移。再做不同深度/画面区域和不同工作区位置的交叉检查。样本量、测量精度及允许误差按实际抓取余量设定，不把某个通用 mm 数当作已经满足的标准。

### C. 不将仿真 profile 直接改名为实机 profile

- 实机配置使用真实反馈与真实时钟；不使用 Gazebo 物体真值、DetachableJoint、fake joint state 或仿真 `world` 坐标替代现场量测。
- 当前 `realman_moveit_gz.launch.py` 是仿真启动入口，不是实机启动入口。实机 observer/执行映射须独立验证，不能直接运行 README 中的仿真 launch 来接现场设备。
- 旧 `/manipulation/rm65b/target_pose` 是收到即规划执行的入口；影子阶段不启用它。`set_goal_pose` 只是面板预览，但仍应核对实际 ROS 图。
- 面板 TCP 默认 0.1 m/s、输入上限 2 m/s、“不限”和规划倍率 1 都是软件配置能力，**不是现场批准的安全速度**。实机速度、加速度和工具负载限制应在厂家/执行层落实，不能只依赖可编辑 UI；本清单不提高任何硬件限值。
- 仿真夹持固定附着不代表真实夹持。实机 attach 应跟随确认的夹持/释放事实，不能在闭爪命令刚发出时就假定物体已拿起。
- MTC、普通 A→B、旧终端执行器的限速与取消路径分别验证；面板设置不是全工程统一限速器。

## 现场观察命令：只读、不启动设备

以下命令仅检查已经由现场负责人启动的 ROS 图；节点/topic/frame 名以现场为准。先记录 `ROS_DOMAIN_ID`，不要使用自动探针来试探机器人能不能运动。

```bash
ros2 node list
ros2 topic list -t
ros2 action list -t
ros2 topic info /joint_states -v
ros2 topic echo /joint_states --once
ros2 topic hz /joint_states
# 找到实际节点名后逐个检查，而不是假设已有统一硬件 bringup：
ros2 param get /YOUR_DRIVER_NODE use_sim_time
# 只有已核对模型/设备 frame 后，再观察真实坐标链：
ros2 run tf2_ros tf2_echo base_link YOUR_TCP_FRAME
ros2 run tf2_ros tf2_echo YOUR_FLANGE_FRAME YOUR_CAMERA_OPTICAL_FRAME
```

`scripts/test_operator_panel.sh` 会执行仿真动作；`verify_realman_*` 是当前仿真运行检查，不能改个 topic 就拿到实机执行。已有动态状态/TF 的检查还应核对采样时刻与有效性，不能只看终端最后一行。

## 每项只保存这些记录

| 字段 | 要记录的内容 |
| --- | --- |
| 条目/结论 | 主线编号；未做/通过/失败/需复测；失败原因和下一项动作 |
| 环境版本 | Git SHA、设备/固件/驱动、相机序列与配置、工具/夹爪状态、标定版本 |
| 约束 | 单位、frame、实际限速/限位、负载、测试区域和预先定义的误差判据 |
| 原始证据 | 命令与实际反馈、厂家结果/报警、图像、TF/时间戳、独立量测、必要的 rosbag 路径 |
| 汇总 | 样本数、均值/最大误差/离散性、动作时间、停止/恢复结果 |

配置和摘要可以入 Git；图像、rosbag、日志和设备私密信息留在受控存储，用路径/校验和关联。不要提交厂商账号、网络凭据或密钥。

## 第一轮与后续探索如何取舍

第一轮优先产出：设备/版本表、可靠真实反馈、夹爪独立结论、工具/TCP/负载配置、手眼独立复核结果、工位场景。这些完成后再尝试一个已知位置的单步抓放。

随后再做：多位置/多姿态重复性与绝对误差分开测量、夹持可靠性/滑移及不同工件、速度—精度—节拍对比、边界场景/失败恢复。位置—姿态地图在校准模型上离线生成，用来辅助选点；不通过实机穷举运动寻找极限，也不把它作为首轮抓取的必备新框架。
